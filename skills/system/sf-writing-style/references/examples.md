# Before/after rewrite examples

Worked pairs applying the sf-writing-style rules. Each "before" is the kind of dense, dash-heavy prose the rules exist to prevent.

## 1. Dense description paragraph

Before:

> That develop push runs the same QA recipes in CI, builds and pushes the app images to the shared registry, helm-deploys every app into the project's cluster namespace (group GitLab Agent, zero per-project infra variables) and deploys the PostgreSQL alongside them (predeploy stage). Merge requests build the production image as proof without pushing. Production (`main`) is always customized per project: the packages automate up to develop, by platform standard.

After:

> That develop push triggers, in order:
>
> - **The same QA recipes** you ran locally, in CI (literal parity).
> - **Image build and push** for every app, to the shared registry.
> - **PostgreSQL deployment** first (predeploy stage), then **helm deployment of every app** into the project's cluster namespace (group GitLab Agent, zero per-project infra variables).
>
> Merge requests build the production image as **proof only** (no push).
>
> Production (`main`) is always customized per project: **the packages automate up to develop**, by platform standard.

## 2. Label-style lead-ins for a contract or spec

Before:

> The mechanism that makes this work across frameworks is the script-name contract: every app has `lint`, `lint:fix`, `typecheck`, `test` scripts; the runners call names, each app brings its own framework-correct configuration (Nest tests run vitest with the SWC transform for decorators; Next tests run vitest in the node environment). You never configure this: `ts-create-app` wires it.

After:

> The mechanism that makes this work across frameworks is the **script-name contract**:
>
> - **Every app has the same script names.** `lint`, `lint:fix`, `typecheck`, `test`.
> - **The runners call names.** Each app brings its own framework-correct configuration (Nest tests run vitest with the SWC transform for decorators; Next tests run vitest in the node environment).
> - **You never configure this.** `ts-create-app` wires it.

## 3. Takeaway extraction

Before:

> Most of the infrastructure around them (justfile recipes, Makefile, CI pipeline, tools container) is generated by Firestarter packages and regenerated on every `fs-cli pkg:install`, and the root `AGENTS.md` header lists what is package-owned, so as a rule of thumb, if a file says "do not edit", edit the package instead, or the change evaporates.

After:

> Most of the infrastructure around them (justfile recipes, Makefile, CI pipeline, tools container) is **generated by Firestarter packages** and regenerated on every `fs-cli pkg:install`. The root `AGENTS.md` header lists what is package-owned.
>
> **Rule of thumb:** if a file says "do not edit", edit the package instead, or the change evaporates.

## 4. Dash rewrites

Four tools replace every em or en dash: period, comma, colon, parentheses.

| Before                                                           | After                                                                    | Tool used   |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------ | ----------- |
| `The build failed — the registry token had expired.`             | `The build failed: the registry token had expired.`                      | colon       |
| `Run the linter — it catches most of these — before pushing.`    | `Run the linter (it catches most of these) before pushing.`              | parentheses |
| `The cache is warm — subsequent runs take seconds.`              | `The cache is warm. Subsequent runs take seconds.`                       | period      |
| `Pages 10–20 cover the API.`                                     | `Pages 10 to 20 cover the API.`                                          | rewrite     |
| `Everything is containerized — node, pnpm, even the docker cli.` | `Everything is containerized, including node, pnpm, and the docker cli.` | comma       |

## 5. Counter-example: do not bulletize narrative

An ADR context section, correctly left as paragraphs:

> We evaluated moving the QA pipeline from per-app configs to workspace-level runners in Q2. The per-app approach had drifted: three apps pinned different eslint majors, and a fix in one config never reached the others. The team spent two sprints reconciling rules before any migration could start.
>
> Workspace-level runners fix the drift but concentrate risk: one bad config change breaks every app at once. We accepted that trade-off because CI parity makes the breakage visible within minutes.

The same content wrongly bulletized (fragment confetti, do not do this):

> - **Evaluated** moving QA pipeline in Q2
> - **Per-app approach drifted.** Three apps, different eslint majors
> - **Fix in one config.** Never reached others
> - **Two sprints** reconciling rules
> - **Workspace runners.** Fix drift, concentrate risk
> - **Trade-off accepted.** CI parity, breakage visible in minutes

The bullets are not parallel items; they are one story chopped into fragments. The causal connections ("because", "before any migration could start") carried the meaning, and the bullets destroyed them.
